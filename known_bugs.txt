Crashes (RESOLVED in v1.1.0-beta5 — see STAGE1_GAMETHREAD_NOTE.md / CRASH_HANDOFF.md):

- [FIXED in 1.1.0-beta5] The recurring access-violation crash (the long-standing one). Root cause:
  warding mutated live render/collision state from UE4SS LoopAsync callbacks (a SEPARATE async thread,
  NOT the game thread), racing the engine's render/cluster-tree workers. Fix: layer-3 book-pile writes
  moved to the game thread (ExecuteInGameThread, BOOK_VIS_GAMETHREAD) + a world-epoch teardown guard.
  Confirmed by a full 1-4h crash-free playthrough. Layers 1 & 2 remain off-thread (rarer race; the
  game-thread "pump" is the planned follow-up to bring them on without UE4SS #1180).

- [FIXED in 1.1.0-beta5] 12AF29C8 / 7567C016 — EXCEPTION_ACCESS_VIOLATION reading 0x1e3010030 /
  0x300000037 (use-after-free read), going to the TITLE / MAIN MENU (title->M01 LoadMap / world
  reload). First seen 2026-06-02 21:11 (beta4+Stage1), then REPRODUCED going to the main menu at 22:01.
  Cause: a deferred book-pile-hiding pass (apply_book_visibility, marshaled to the game thread) ran on
  the FREED old-world HISM array during the reload — a native AV that Lua pcall can't catch.
  Fix: a world-epoch counter (reset_hism_state bumps it; the game-thread closure bails if it changed
  between scheduling and running). Confirmed catching the race live (b2-stale-world marker, no crash).
  Artifacts: "crash reports/title-reload 2026-06-02 2111..." and ".../mainmenu-AV 2026-06-02 2201...".

Book visibility edge cases (rare ~3/3072 over a 1-4h run; ADDRESSED in v1.1.0-beta6, field-validation pending):

- "Visible but not grabbable" — a warded book briefly shown by the game's view-dependent toggle. beta6:
  a SetActorVisible PRE-hook keeps warded books hidden at show-time (BOOK_EVENT_ENFORCE).
- "Vanishes when looked at / picked up, fine after dropping" — an unwarded book stuck hidden. beta6:
  a SetActorVisible POST-hook re-shows it (BOOK_EVENT_REVEAL).
  These are the two directions of the same actor-vs-pile desync. Confirm via the [book-hook]
  ENFORCE/REVEAL log counts over a full playthrough + tester reports. If REVEAL stays 0 but vanishing
  books persist, symptom 2 isn't the stale-hide we targeted — look elsewhere. See WARDING_SYNC_PLAN.md.

1.1.0 Known Issues:

- "Visible in the pile, invisible when held" (hidden mode only). A received (unwarded) book occasionally
  renders invisible the instant it's grabbed — it's fine in the shelf pile and stays grabbable. Rare and
  RANDOM: different books each session, sometimes 1, sometimes a few, sometimes a whole series.

  WORKAROUNDS (either clears it; nothing is lost, the save is never corrupted):
    * Throw the affected book OUT OF BOUNDS. The game's stray-book recovery teleports it back to its slot a
      few seconds later and it returns visible. Lightest fix — no reload, no progress lost.
    * Or go to the title screen and Continue, or relaunch. Per-session only; affected books come back normal.

  ROOT CAUSE (confirmed via live debugging 2026-06-05): a stuck RENDER PROXY on the held actor's SM_Book_1.
  The actor is "visible" by every readable flag but the renderer never draws it. A side-by-side capture showed
  the broken book IDENTICAL to a healthy one on every reflected field (bHidden=false, mesh shown, scale 1.0,
  opacity nil, bRenderInMainPass=true, bounds/owner normal); the ONLY signal is WasRecentlyRendered=false. The
  fault is BELOW the reflection layer — nothing the mod can read or set is wrong.

  NOT fixable from the mod side (confirmed live): a full render-proxy rebuild does NOT clear it — SetVisibility
  toggle, SetStaticMesh cycle, actor hide/show, and the game's own SetNewMesh / RefreshInfo all produce an
  equally-invisible proxy. Only a BRAND-NEW component clears it, which happens on a full actor re-spawn (reload)
  or when the game recovers an out-of-bounds book to its slot. (Destroying the actor from Lua to force a
  re-spawn is NOT viable — it desyncs the spawner's bookkeeping and corrupts the save.)

  Detection is grab-only: the book is fine in the pile and breaks the instant it's picked up, so there's no
  pre-grab state to scan for, and an automatic in-place heal isn't possible without the disruptive
  fling-and-recover. Confirmed hidden-mode only (stacks never hides books); runtime/per-session only; it's the
  actor's SM_Book_1, not the pile/HISM. BOOK_ACTOR_RECONCILE still heals the unrelated flag-based variants.

  Ruled out: opacity, WPO / CustomPrimitiveData displacement, transform / mesh-Z, scale, the bHidden /
  mesh-visibility flags, null mesh, tint corruption, BookInfo (RefreshInfo, called 3,467x in one session).

  Diagnostics ship via the grab path (BOOK_EVENT_HOOKS, on by default) — grep UE4SS.log for:
    [book-hook] *** INVISIBLE-CONFIRMED ***  a held book confirmed genuinely not-drawn (~0.6s after grab)
  (The passive BOOK_INVIS_SCAN ships OFF — without a camera-FOV filter "shown but not drawn" is dominated by
  normal off-screen frustum culling and floods the log. Toggle via Scripts/diag_flags.lua; changes no gameplay.)

- Intermittent native crash / freeze from the warding-vs-engine render race (hidden mode). Two shapes seen:
    * During play: a routine 5s warding pass (esp. the OFF-thread Layer-2 bookcase ward) races the engine's
      parallel render reads -> a native access violation the mod can't catch. Decoupled (the crash_trace tail
      is heartbeats, no mod write in flight). Rare; previously ~3/3072 books over a 1-4h run.
    * Return-to-menu: a heavy ward pass right before the world reload leaves book/bookcase/HISM components
      mutated, and the engine's teardown of them hangs (multi-minute freeze) then crashes.
  Long-standing (see CRASH_HANDOFF.md). rc3's serialized ward pump fixed the off-thread RENDER race (Layers 1-2
  writes now drain through one game-thread pump). But rc3 still crashed (5 reports): a SEPARATE cross-thread
  LUA-STATE race. UE4SS runs the mod's Lua on a background thread, yet RegisterHook callbacks AND the pump's async
  ExecuteInGameThread closures run Lua on the GAME thread -- so game-thread Lua iterating/allocating against the
  same Lua tables the mod thread rewrites (e.g. the SetActorVisible hook walking _series_unlocked while an item
  arrival rebuilt it) corrupts the Lua heap -> a next/compare error or a UE4SS abort(). rc4 FIXES this: the game
  thread now only reads immutable mod-thread snapshots, atomically-swapped tables, or scalar flags
  (snapshot-before-marshal for the L1/L2 pump passes; a precomputed _unwarded_snapshot for the hooks;
  FinishRow/SaveGameData/OnLevelUp progress writes deferred to the 3s mod loop). Field-validated clean by the
  maintainer. The return-to-menu teardown FREEZE remains a separate, still-open follow-up (the world-epoch guard +
  queue-flush prevent the CRASH there, but the Menu->Continue freeze is not yet mitigated).

  REPORTING (on the 1.1.0 build, please): if you crash or freeze, send the crash-report folder, especially:
    - Mods/Librarian-AP/crash_trace.log   (breadcrumb ledger -- the TAIL names the last mod op before death)
    - .../Win64/UE4SS.log                  (last 100-200 lines)
    - one line on what you were doing (placing a row, returning to menu, walking a shelf, ...)
  Confirm the trace header says mod=1.1.0-rc4 (older builds don't help). If you crash, the crash_trace tail +
  the UE4SS.log tail (look for a Lua 'next'/'compare' traceback or an 'abort') tell us whether a game-thread
  shared-table access slipped through.
